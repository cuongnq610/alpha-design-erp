# Sync-Error Quarantine & Client Validation Parity — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stop a single invalid record from permanently breaking Cloud sync (and bricking the whole app into read-only), and prevent invalid records from being created in the first place.

**Architecture:** Two independent phases.
- **Phase 1 — Resilience (quarantine):** When the `apply_entity_change` RPC *permanently rejects* an outbox item (server-side validation exception), move that item to a new `quarantine` store instead of re-throwing and aborting the whole sync loop. Keep `status='online'` so the app stays writable. Surface quarantined records in the Cloud admin screen with the exact server error, and let the user re-queue or discard them. *Transient* errors (network, auth) keep the current retry-forever behavior.
- **Phase 2 — Prevention (validation parity):** Add a shared client-side validator that mirrors the server's `validate_entity_payload` rules, run at form-submit time before a record is ever saved locally / enqueued, so bad data never reaches the outbox.

**Tech Stack:** Vanilla ES5-ish browser JS (no framework, no bundler). `alpha-sync.bundle.js` is a hand-authored minified file that is the source of truth (copied verbatim to `public/` by `scripts/build-public.mjs`). Supabase Postgres RPC. Node's built-in `node:test`/`assert` for tests (repo convention is static source-marker assertions — see `tests/no-silent-mutation-security.test.mjs`).

## Background / Root Cause (verified)

- `cloud-v2.js:283-291` `syncCloud()` calls `AlphaOnline.syncNow()` → minified `Or()` → `pt()` sync loop.
- `pt()` loops `u.outbox`, calling `.rpc("apply_entity_change", …)`. On any error the `catch` does `throw (u.status="error", X(), F(), w)` — **re-throwing aborts the whole loop**, the failed item is **never removed from `u.outbox`**, so every future sync re-hits the same poison record.
- Server `app.validate_entity_payload` (migration `033_entity_payload_integrity_v453.sql`) raises `REQUIRED_FIELD`/`INVALID_NUMBER`/`INVALID_DATE`/`INVALID_ENUM`/`INVALID_REFERENCE`/`FORMULA_MISMATCH`/`DUPLICATE_KEY`/… with SQLSTATE `22023`/`23505`/`23503`.
- `production-guard.js:19` `canWrite()` returns `…&&syncStatus.status==='online'&&…`. Poison record → `status='error'` → **entire production app becomes read-only** (`production-guard.js:67-68` block all edit/delete/submit).
- Client `validate` functions exist per collection (`app.js:2824-2862`) but are inconsistent (e.g. `accounts` only checks duplicate code, not code format/length/enum that the server enforces).

**Net effect:** one record that passes weak client validation but fails server validation permanently jams sync AND flips the app to read-only until browser storage is cleared.

function validateEntityPayload(collection, data, db = {}) {
  const errors = [];
  const txt = (...keys) => { for (const k of keys) { const v = String(data?.[k] ?? '').trim(); if (v) return v; } return ''; };
  const num = (...keys) => { const v = txt(...keys); if (!v) return null; if (v.length > 80 || !/^[+-]?[0-9]+(\.[0-9]+)?$/.test(v)) { errors.push(`INVALID_NUMBER: ${keys[0]}`); return null; } return Number(v); };
  const req = (label, max, ...keys) => { const v = txt(...keys); if (!v) errors.push(`REQUIRED_FIELD: ${label}`); else if (v.length > max) errors.push(`FIELD_TOO_LONG: ${label}`); return v; };
  const isoDate = (label, ...keys) => { const v = txt(...keys); if (v && !/^\d{4}-\d{2}-\d{2}$/.test(v)) errors.push(`INVALID_DATE: ${label}`); return v; };
  const rules = {
    accounts: () => {
      const code = req('accounts.code', 32, 'code'); if (code && !/^[0-9A-Za-z._-]+$/.test(code)) errors.push('INVALID_CODE: accounts.code');
      req('accounts.name', 240, 'name');
      const type = txt('type'); if (!['asset','liability','equity','revenue','expense'].includes(type.toLowerCase())) errors.push('INVALID_ENUM: accounts.type');
    },
    projects: () => {
      req('projects.code', 64, 'code'); req('projects.name', 240, 'name');
      req('projects.clientId', 64, 'clientId'); req('projects.pmId', 64, 'pmId');
      isoDate('projects.startDate', 'startDate');
      const cv = num('contractValue'); if (cv !== null && cv <= 0) errors.push('NUMBER_OUT_OF_RANGE: projects.contractValue');
    },
  };
  (rules[collection] || (() => {}))();
  return { ok: errors.length === 0, errors };
}
